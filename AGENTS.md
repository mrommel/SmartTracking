# SmartTracking — AI Agent Guide

Django 6.1 issue/ticket tracker. Single app (`tracking/`) under the `setup/` project. SQLite dev DB, server-rendered Bootstrap 5 templates. No JS framework. A plain-Django JSON REST API (no DRF) lives in the `tracking/api/` package, mounted at `/tracking/api/` and exposed as MCP tools.

**Where to find the ticket system:** The MCP server is the primary documentation source. Start it with `make run` (port 8091) and call `get_meta` for all enums (types, states, priorities) and the full state-transition graph. Use the MCP tools (`list_tickets`, `create_ticket`, `transition_ticket`, etc.) to interact — no need to read MD files for ticket domain knowledge. See **Workflows** below to start it.

## Architecture
- `setup/` is the Django project (settings, root URLconf, WSGI/ASGI). `setup/urls.py` mounts everything under `tracking/` and redirects `/` → `/tracking/dashboard`.
- `tracking/` holds all domain logic. Models in `tracking/models.py`:
  - `Project` — groups tickets; has a unique uppercase `key` (e.g. `SMT`) used as a ticket-ID prefix. Owns `Sprint`, `Component`, and `Label` (all project-scoped via `unique_together=["project", "name"]`).
  - `Ticket` — the work unit. Type (`task`/`bug`/`story`/`epic`)/State/Priority are `TextChoices`/`IntegerChoices` enums defined inline. Has `estimation`, `due_date`, `sprint` FK, `parent_epic` self-FK (epics group child tickets via `related_name="child_tickets"`), and `components`/`labels` M2M.
  - `Comment` and `Attachment` — attached to a `Ticket` (comments ordered oldest-first; attachments validate extension/MIME against `_ALLOWED_EXTENSIONS`, 10 MB cap, stored under `media/attachments/<KEY>/<pk>/<ext>/`).
  - `TicketRelation` — a directed link between two tickets (`RelationType`: related_to/blocked_by/tested_with/is_parent/is_child). **Relations are symmetric**: `TicketRelation.save()` auto-creates the reverse counterpart from `Ticket._REVERSE_LABELS`, and deletes must remove both directions (see `ticket_relation_delete`). Only tickets in the *same project* may be related.
  - `Version` — a release; `Ticket.fix_version` FK + `affects_versions` M2M. Drives the roadmap and generated release notes (`version_views.py`).
  - `WorkLog` — per-user time entry (`time_spent` minutes, `original_estimate`/`remaining_estimate` hours, `date`). Ticket rollups: `total_spent`, `total_original_estimate`, `total_remaining_estimate`, `progress_percent`.
  - `TicketActivity` — audit trail (`Action`: TICKET_CREATED / STATE_CHANGED / SPRINT_CHANGED / TITLE_CHANGED …, plus `field_name`/`old_value`/`new_value`). **Writing a `TicketActivity` is what fans out notifications** — see Signals below.
  - `Notification` (verbs ISSUE_ASSIGNED / STATE_CHANGED / COMMENTED / MENTIONED_IN_COMMENT, unique per `(ticket, recipient, verb)`) and `Watcher` (unique per `(ticket, user)`) — the subscribe/notify pair.
  - `SavedFilter` (`filters_json` dict + `is_active`, per user+project), `UserProfile` (OneToOne with `User`, `avatar` file + `avatar_url` property), `CommentEditHistory` (old/new body per edit), `SprintMetrics` (OneToOne with `Sprint`: velocity, completion, waste ratio).
- `Sprint` — time-boxed iteration. Every project has a **Backlog pseudo-sprint** (`pk=1`, `name="Backlog"`, `is_backlog` property); tickets with `sprint=None` mean Backlog. At most **one active sprint per project** (enforced in `Sprint.save()`). Close a sprint via `close_with_action(action, target_sprint_id)` where action ∈ `backlog`/`sprint`/`keep` — never delete or clear the backlog sprint.
- **State machine lives in the model, not the view.** `Ticket.TRANSITIONS` maps each `State` to its reachable states; use `ticket.allowed_transitions()` and `ticket.can_transition_to(new_state)` rather than hardcoding state logic. `TicketTransitionForm` builds its choices from `allowed_transitions()` and re-validates via `can_transition_to()` in `clean_state`.
- Views are **function-based**, thin, and return `render(...)`. `tracking/views/` is a **package split by domain** — `project_views.py`, `ticket_views.py`, `sprint_views.py`, `report_views.py`, `component_views.py`, `label_views.py`, `version_views.py`, `notification_views.py`, `watcher_views.py`, `bulk_views.py`, `saved_filter_views.py`, `user_views.py`. `__init__.py` is intentionally empty: `tracking/urls.py` imports each module under a short alias (`import tracking.views.ticket_views as _tv`) — add new views to the matching module, never to a monolithic `views.py`.
- State changes go through the dedicated `ticket_transition` POST view + `save(update_fields=["state", "updated_at"])`, never via `TicketForm` (which deliberately omits `state`).
- **Signals (`tracking/signals.py`, wired in `TrackingConfig.ready()`)** turn model writes into notifications: `post_save` on `TicketActivity` → `handle_ticket_activity` (assignment/state/sprint/title events), `post_save` on `Comment` → `handle_comment_saved` (notifies watchers + reporter, and parses `@mentions` via `MENTION_RE`). Use the `add_watcher`/`remove_watcher` helpers instead of touching `Watcher` directly.
- User feedback uses `django.contrib.messages`; `base.html` renders them as Bootstrap alerts.

## Conventions
- **Indentation is TABS** in Python and templates (see `models.py`, `tracking/views/*.py`). Match the surrounding file — some lines in `settings.py`/`urls.py` are space-indented; don't reformat wholesale.
- Every user-facing model field/label uses `gettext_lazy as _` for i18n (`de` + `en` configured). Wrap new labels in `_(...)`.
- Query performance: use `select_related(...)` for FK access and `annotate(Count(...))` for counts (see `ticket_list`, `project_list`).
- Templates extend `tracking/base.html`; reusable snippets are `_`-prefixed partials pulled in with `{% include %}` and `with` (e.g. `_state_badge.html`). Prefer `{{ ticket.get_<field>_display }}` and `humanize` filters (`naturaltime`). Partial-only views (e.g. `project_board_partial`) render a fragment for in-page refreshes.
- Custom template tags in `tracking/templatetags/` — `{% load %}` them where used:
  - `type_badge.py`: `{% type_badge ticket %}` / `{% priority_badge ticket %}` (Bootstrap `text-bg-*` variants).
  - `markdown_filters.py`: the `markdown` filter (`mistune`, `escape=True`) for ticket/comment bodies, plus `notifications_count`, `user_initials`, `user_avatar_color`.
  - `avatar_filters.py`: `{% avatar_url user size %}` (falls back to the UI Avatars service when `UserProfile.avatar` is unset).
  - `dict_tags.py`: `getdict` / `getint` for dict lookups in templates.
- URL names are flat (no namespace): reference as `{% url 'ticket_detail' ticket.pk %}` / `redirect("ticket_detail", pk=...)`.
- All pages live in `templates/tracking/` and extend `tracking/base.html` (including `dashboard.html`).

## Workflows (use the Makefile — it pins `python3.12` inside `.venv`)
- Run dev server (loads `.env`, port 8092) **and the bundled MCP server (port 8091)**: `make run` (the MCP server is supervised and auto-restarts after 1 s if it dies)
- MCP over stdio (for editors that spawn the server): `make mcp-stdio`. Probe a running instance: `make mcp-health` (curls `/health`, non-zero exit when down).
- Create/apply migrations: `make makemigrations` (runs `sqlmigrate tracking $(MIGRATION)`, default `0001` — pass the real number: `make makemigrations MIGRATION=0015`) / `make migrate`
- Tests + coverage: `make test` (`coverage run --source=tracking manage.py test tracking` + `coverage report`), then `make coverage-report` → `htmlcov/index.html`; `make coverage-clean` erases the data.
- Translations: `make preparetranslations` then `make compiletranslations` (locale at `tracking/locale/`); `make check-translations` runs `scripts/check_translations.py` (polib) to find missing/fuzzy entries.
- Database backup: `make backup` (optionally `make backup KEEP=30`) → writes `backups/yyyy-mm-dd db.sqlite3.zip` via the `backup_db` management command (`tracking/management/commands/backup_db.py`, SQLite online-backup snapshot; `backups/` is gitignored). Flags: `--output-dir`, `--keep N`, `--no-overwrite`, `--database`.
- Rebuild venv: `make clean && make venv`
- Direct manage.py calls must use the venv interpreter: `./.venv/bin/python3.12 manage.py <cmd>`.

## Integrations / gotchas
- `slippers` is registered as a template builtin — its component tags work without `{% load %}`. Reusable UI components are registered in `tracking/templates/components.yaml` and live in `tracking/templates/tracking/components/`: `badge` (props `variant`, `pill`; use as block `{% #badge variant="primary" %}…{% /badge %}`) and `state_badge` (prop `ticket`, maps state→variant). **Never put Django tag syntax (`{% %}`) inside `{# #}` comments in `.html` or `components.yaml`** — multiline `{# #}` isn't supported and the tags get parsed for real (caused component self-recursion).
- `django-autocomplete-light` (`dal`, `dal_select2`) powers admin `autocomplete_fields` (see `tracking/admin.py`); also `crispy_forms` + `crispy_bootstrap5` (pack = `bootstrap5`), `django_extensions`, `django_admin_inline_paginator`, and `mistune` (markdown rendering). Deps are pinned in `requirements.txt` (`mcp`/`httpx` back the bundled MCP server; `coverage`, `ruff`, `black`, `polib` are the tooling deps). Formatter/linter config lives in `pyproject.toml` (Black + Ruff).
- Env vars load from `.env` via `make run` (copy `.env.example`). `TRACKING_API_TOKEN` is the only app var. `.env` is gitignored; `.env.example` is the tracked template.
- Tests live in the `tracking/tests/` package: `test_models.py`, `test_views.py`, `test_api.py`, `test_ui.py` (per-view render/status coverage), `test_components.py` (slippers components), `test_mcp_server.py`, `test_backup_db.py`, `test_settings.py`, `test_sprint_create.py`, `test_user_views.py`, `test_worklog.py`. Run with `make test` (or `./.venv/bin/python3.12 manage.py test tracking`). API tests set the token via `@override_settings(TRACKING_API_TOKEN=...)`.
- Settings are dev-only (`DEBUG=True`, hardcoded `SECRET_KEY`, console email backend). Don't rely on production config.

## REST API (`tracking/api/`, `/tracking/api/`)
- Plain-Django JSON views (no DRF), function-based, CSRF-exempt. `tracking/api/` is a **package split per resource** — `meta.py`, `schema.py`, `projects.py`, `tickets.py`, `comments.py`, `components.py`, `labels.py`, `attachments.py`, `sprints.py`, `active_sprints.py`, `worklogs.py`, `notifications.py`, `watchers.py` — with all routes in `tracking/api/urls.py` (`include()`d from `tracking/urls.py`). URL names are `api_`-prefixed. Per-resource modules expose `collection` / `detail` functions; add a new resource as a new module + a line in `urls.py`.
- Shared helpers live in `tracking/api/_common.py`: `parse_json`, `_page_json` (pagination envelope), `_serialize`/`_serialize_list` (uses a model's `_data()` when defined), `_valid_required`/`_valid_optional`, `require_api_auth`, and a local `require_http_methods` that already stacks `@csrf_exempt` → `@require_api_auth` → method check — decorate views with just `@require_http_methods([...])`.
- OpenAPI 3.1.0 spec at `GET /tracking/api/schema/` — loads into any OpenAPI viewer (Swagger UI, ReDoc, etc.). Schema covers all endpoints, request/response bodies, parameter descriptions, and Bearer/Cookie auth schemes.
- List endpoints (`collection` GET views) return a **paginated envelope**:
  `{ "count": N, "pagination": {"next": …, "previous": …}, "results": [...] }`.
  Query params: `page` (default 1, 1-based) and `page_size` (default 25, max 100).
  Single-object endpoints (`GET <pk>`, `POST`, `PATCH`, `DELETE`) are unchanged.
- Endpoints: `GET /api/meta/` (enums — incl. relation types — + transition graph for discovery), `GET|POST /api/projects/`, `GET /api/projects/<key>/`, `GET|POST /api/tickets/` (filter `?project=&state=&assignee=&component=&label=`; `assignee=me|unassigned`), `GET|PATCH /api/tickets/<pk>/`, `POST /api/tickets/<pk>/transition/`, `POST /api/tickets/<id>/relations/add/` + `DELETE /api/tickets/relations/<pk>/delete/`, `GET|POST /api/tickets/<pk>/worklogs/` + `DELETE /api/worklogs/<pk>/delete/`, `GET|POST /api/comments/` (`?ticket=`) + `/api/comments/<pk>/`, `GET|POST /api/components/` + `GET|PATCH|DELETE /api/components/<pk>/`, `GET|POST /api/labels/?project=` + `/api/labels/<pk>/`, `GET|POST /api/attachments/?ticket=` (multipart upload) + `GET|DELETE /api/attachments/<pk>/`, `GET /api/notifications/` + `POST /api/notifications/<pk>/mark_read/`, `/api/notifications/mark_all_read/`, `/api/notifications/<pk>/delete/`, `GET /api/watchers/<ticket_pk>/` + `/api/watchers/<ticket_pk>/remove/<user_pk>/` and the workspace-level `/api/watchers/workspace/{,add/,remove/<pk>/}`, `GET /api/sprints/<key>/` (project sprints), `POST /api/sprints/<key>/create/`, `GET|PATCH|DELETE /api/sprints/<pk>/` (DELETE refuses the backlog), `POST /api/sprints/<key>/<sprint_pk>/close/`, `GET /api/sprints/<key>/active/tickets/` (tickets of the project's single active sprint — `sprint: null` + empty list when none is active).
- State changes go **only** through `/transition/`, which reuses `ticket.can_transition_to()` (returns 409 + `allowed_transitions` on illegal moves); `PATCH` rejects a `state` key. Mirror the HTML views' state-machine discipline for any new endpoint.
- MCP integration: `make run` also starts a bundled MCP server (see Workflows above) wrapping these endpoints as agent tools (~25 tools: `get_meta`, `list_tickets`, `create_ticket`, `transition_ticket`, sprint/component/label/attachment/relation CRUD). See `mcp_server.md` for client config (VS Code / Claude Desktop); ports/URL are configurable via `MCP_HOST`/`MCP_PORT`/`SMARTTRACKING_URL`.

## Authentication
- **All HTML views are `@login_required`** (`tracking/views/*.py`), except the public `health_check` (`/tracking/health/`). Login/logout use Django's built-in `LoginView`/`LogoutView` (URL names `login`/`logout`); template is `templates/registration/login.html`. Settings: `LOGIN_URL="login"`, `LOGIN_REDIRECT_URL="dashboard"`, `LOGOUT_REDIRECT_URL="login"`. Logout is a POST form in `base.html`.
- **API endpoints use `@require_api_auth`** (`tracking/api/_common.py`): accepts a logged-in session *or* a bearer token (`Authorization: Bearer <token>` / `X-API-Token`) compared against `settings.TRACKING_API_TOKEN` (from env `TRACKING_API_TOKEN`, empty disables token auth). Unauthenticated → 401 + `WWW-Authenticate: Bearer`. Decorator order is `@csrf_exempt` → `@require_api_auth` → method check, already bundled in the local `require_http_methods`.
- Create users via `./.venv/bin/python3.12 manage.py createsuperuser`; run the API with a token: `TRACKING_API_TOKEN=... make run`.
